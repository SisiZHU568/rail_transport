# DPPO 快时间尺度凸优化调度器设计

## 1. 目标

本阶段用真正的数学求解器替换 DPPO 主算法中的快层枚举修复。慢时间尺度
DPPO 决定整条 SFC 的副本数量、部署节点和保留时间；快时间尺度只在这些
已经部署的副本之间分配当前时隙请求并确定执行路径。

快层采用 CVXPY 建模、CLARABEL 求解。求解失败时直接拒绝当前请求，不能
调用旧枚举器、启发式搜索或其他求解器作为安全回退。

设计参考双时间尺度边缘服务研究中“慢层服务部署、快层任务调度”的职责划分。
参考文献：Yang Li 等，*Two-Timescale Dynamic Service Deployment and Task
Scheduling with Spatiotemporal Collaboration in Mobile Edge Networks*，
arXiv:2508.16293v1。

## 2. 本阶段边界

### 2.1 实现内容

- 在慢层部署不变的前提下生成完整 SFC 执行路径；
- 允许一个快时隙中的请求批次分配到多条路径；
- 建立请求分流凸优化模型；
- 使用 CLARABEL 求解连续分流比例；
- 将连续比例确定性转换为整数请求数；
- 按多个调度批次执行请求并汇总成本、时延和成功率；
- 把求解失败作为正式训练反馈，而不是隐藏问题；
- 输出求解状态、目标值、耗时和路径分配，供论文实验使用。

### 2.2 不实现内容

- 快层不迁移、增加或删除慢层部署的 VNF 副本；
- 不使用 HiGHS；
- 不使用旧枚举式 `FastFeasibilityOptimizer` 作为回退；
- 不在本阶段加入基线算法或独立算法对比；
- 不引入新的奖励权重；
- 不把 CLARABEL 放到 GPU，GPU 继续只服务于 DPPO 训练。

## 3. 双时间尺度职责

慢层 DPPO 决定：

- 每个 VNF 的副本数量；
- 副本部署节点及主备顺序；
- 主副本与备用副本的保留时间；
- 部署意图的慢窗口有效期。

快层凸优化器决定：

- 当前正常副本能组成哪些完整 SFC 路径；
- 当前请求批次在各条路径上的分配比例；
- 连续比例对应的整数请求数量；
- 当前时隙是否存在可执行调度方案。

快层不能修改慢层部署。若慢层方案因故障、资源或可靠性问题无法支撑当前请求，
快层返回不可行，训练环境据此惩罚慢层策略。

## 4. 总体数据流

```text
DPPO 慢层动作
    ↓
动作投影生成 SFCDeploymentIntent
    ↓
FastSlotExecutor 读取当前请求、故障和剩余资源
    ↓
FastConvexScheduler 生成合法完整路径
    ↓
CVXPY 构建凸优化问题
    ↓
CLARABEL 求解路径分流比例
    ↓
容量感知确定性取整
    ↓
最终硬约束检查
    ↓
分批执行请求，或直接拒绝
```

## 5. 合法路径生成

对每个 VNF，只读取慢层意图中已经部署的节点。以下节点不能进入路径：

- 当前故障节点；
- 不在该 VNF 部署意图中的节点；
- 网络模型无法到达的节点；
- 会让单条路径预计时延超过 SFC 截止时间的节点组合。

一条完整路径从每个 VNF 的可用副本中选择一个执行节点，并严格保持 SFC
函数顺序。例如三个 VNF 各有两个可用副本时，只产生 `2 × 2 × 2 = 8`
条执行路径。这不是重新枚举副本部署，因为所有节点都来自固定慢层意图。

路径顺序使用节点编号元组稳定排序，保证相同输入重复运行得到相同结果。

## 6. 凸优化模型

设当前时隙请求数为 `Q`，合法路径集合为 `P`。对每条路径 `p` 定义连续变量：

```text
x[p] ∈ [0, 1]
```

`x[p]` 表示当前请求分配到路径 `p` 的比例。

### 6.1 目标函数

快层只有一个目标：最小化当前时隙预计总成本。

```text
minimize Σ x[p] × C[p]
```

`C[p]` 直接使用已有物理计费模型计算：

```text
C[p] = 运行成本 + 网络传输成本 + 冷启动成本
```

三项使用相同成本单位直接相加，不增加人工调节权重。冷启动项在连续模型中
表示选择该路径时的预计启动成本；最终实验成本仍按整数调度后的真实启动事件
计算。

### 6.2 分流约束

```text
Σ x[p] = 1
0 ≤ x[p] ≤ 1
```

这保证全部请求都被分配且不存在负比例。

### 6.3 CPU 容量约束

对每个计算节点 `n`：

```text
Q × Σ x[p] × cpu_demand[p, n] ≤ free_cpu[n]
```

`cpu_demand[p, n]` 是一条请求沿路径 `p` 执行时在节点 `n` 产生的 CPU
需求。若同一路径中的多个 VNF 位于同一节点，其需求必须累加。

### 6.4 部署、内存和可靠性约束

副本数量、部署节点、温实例内存和故障域可靠性属于慢层部署约束。进入凸优化
前必须由现有审计器验证。由于快层不改变部署，审计失败时直接返回不可行，
不能通过重新部署掩盖慢层动作错误。

冷副本在整数调度后被实际选中时会激活内存。容量感知取整必须把这部分内存
计入最终检查；若无法在内存约束内完成全部整数请求分配，则拒绝当前时隙。

现有 `SlotConstraintAuditor` 将增加两个明确入口：部署审计负责副本数量、
温实例内存和可靠性；调度审计负责按全部整数路径批次累计 CPU、激活内存和
执行路径完整性。资源与可靠性公式仍只保留在审计器中，调度器不能复制第二套
最终判定公式。

### 6.5 SLA 约束

预计端到端时延超过 SFC 截止时间的路径在建模前被排除。因此任何正分流比例
只能分配给满足 SLA 的路径。整数调度后仍使用真实执行时延再次检查。

## 7. 容量感知确定性取整

CLARABEL 输出连续比例后，按以下规则得到整数请求数：

1. 每条路径先分配 `floor(Q × x[p])` 个请求；
2. 计算尚未分配的请求数；
3. 按“小数余量降序、路径节点元组升序”处理候选路径；
4. 每次给候选路径增加一个请求前，检查累计 CPU、激活内存和 SLA；
5. 直到全部 `Q` 个请求分配完成；
6. 若剩余请求没有任何可行路径，返回取整失败并拒绝整个时隙请求。

取整过程只把凸优化解转换为可执行整数批次，不重新搜索部署，也不调用旧算法。
连续解是整数调度问题的松弛解和取整指导，不宣称为原离散问题的精确整数最优
解。论文应分别报告连续目标值和最终整数执行成本。

## 8. 代码结构

### 8.1 新文件 `src/fast_convex_scheduler.py`

新增不可变数据对象：

```python
@dataclass(frozen=True)
class FastScheduledBatch:
    request_count: int
    execution_node_ids: tuple[int, ...]


@dataclass(frozen=True)
class FastConvexSchedulingResult:
    succeeded: bool
    solver_status: str
    objective_value: float | None
    solve_time_seconds: float
    path_fractions: tuple[float, ...]
    scheduled_batches: tuple[FastScheduledBatch, ...]
    reason: str
```

新增 `FastConvexScheduler`，职责仅包括：

- 输入检查；
- 合法路径生成；
- 路径成本与容量系数计算；
- CVXPY 问题构建；
- CLARABEL 调用；
- 确定性取整；
- 返回成功或失败结果。

### 8.2 修改 `src/fast_slot_executor.py`

当 `FastSlotInput` 包含 DPPO 的 `deployment_intent` 时：

- 不再调用旧枚举修复器；
- 调用 `FastConvexScheduler`；
- 按 `scheduled_batches` 分批执行 SFC；
- 所有批次成功才把当前时隙记为成功；
- 汇总加权平均时延、逐请求时延样本和真实成本；
- 把求解状态写入快时隙结果。

历史非 DPPO 入口可以继续保留旧优化器，避免本阶段重写无关基线；它不是
DPPO 求解失败后的回退路径。

### 8.3 修改 `src/constraint_audit.py`

在不改变现有单路径接口的基础上增加：

- 部署审计：检查副本数量、部署节点、温实例内存和故障域可靠性；
- 多路径调度审计：按每个 `FastScheduledBatch.request_count` 累计各节点
  CPU，合并所有实际激活的函数—节点实例，再检查内存和路径完整性。

调度器构建模型时可以使用容量系数，但只有共享审计器的最终结果能决定是否
执行，从而避免求解模型和模拟器各自维护一套硬约束真值。

### 8.4 修改 `src/dppo_scenario.py`

从配置创建唯一的 `FastConvexScheduler`，并注入共享快层执行器。DPPO 主算法
不在其他位置创建第二个求解器。

### 8.5 修改 `src/config.py` 与 `configs/debug.yaml`

新增：

```yaml
dppo:
  fast_scheduler:
    solver: CLARABEL
    max_iterations: 200
    feasibility_tolerance: 1.0e-7
```

配置校验规则：

- `solver` 当前必须为 `CLARABEL`；
- `max_iterations` 必须为正整数；
- `feasibility_tolerance` 必须为正有限数；
- 不提供默认回退求解器配置。

### 8.6 依赖

当前运行环境需要安装 CVXPY。CVXPY 安装包同时提供 CLARABEL 接口。代码必须
在依赖缺失时给出明确安装提示，不能静默切换到 SciPy、HiGHS 或旧枚举器。

## 9. 多路径执行与指标

一个快时隙可以包含多个 `FastScheduledBatch`。执行器逐批调用现有 SFC 执行
逻辑，并按请求数量汇总：

- 成功请求数和失败请求数；
- 加权平均端到端时延；
- 用于 P95/P99 的逐请求时延样本；
- CPU 运行成本；
- 网络传输成本；
- 实际发生的冷启动成本；
- 使用中心云的请求数量；
- 求解状态、目标值和求解耗时。

同一函数在不同节点发生冷启动时，记录必须使用“函数 ID—节点 ID”对，不能
只保存函数 ID，否则多路径执行会丢失启动位置。

## 10. 失败语义

以下情况直接拒绝当前请求批次：

- 慢层部署审计不通过；
- 没有合法完整路径；
- CVXPY 或 CLARABEL 抛出异常；
- CLARABEL 状态不是严格的 `optimal`；
- 连续解包含非有限值或超出容差；
- 容量感知取整无法分配全部请求；
- 整数结果最终审计失败；
- 任一执行批次失败。

拒绝时：

- 不调用旧枚举器；
- 不换用第二个求解器；
- 不执行部分请求后把整个批次伪装成成功；
- 把中文原因、原始 solver 状态和求解耗时写入结果；
- 通过既有奖励与 SLA 统计反馈给 DPPO。

无请求时不调用求解器，`request_success` 保持 `None`。

## 11. 核心测试

只运行与本阶段直接相关的核心测试：

1. 低负载时全部请求选择最低成本路径；
2. 单节点 CPU 容量不足时生成多路径分流；
3. 故障节点和超 SLA 路径不会进入解；
4. 取整后的请求总数严格等于输入请求数；
5. 相同输入重复求解得到相同整数分配；
6. 慢层部署审计失败时不调用 CLARABEL；
7. `infeasible`、异常或取整失败时直接拒绝；
8. 使用测试替身证明 DPPO 失败路径没有调用旧枚举器；
9. 多路径调度审计会按所有整数批次累计 CPU 和激活内存；
10. 完成一次“DPPO 部署—凸优化分流—快层执行”的真实慢窗口；
11. 检查求解状态、耗时和路径分配能够从环境信息中读取。

不运行与本功能无关的基线和完整实验套件。

## 12. 验收标准

本阶段完成必须同时满足：

1. DPPO 主算法的快时隙请求调度由 CVXPY + CLARABEL 完成；
2. 快层只使用慢层已经部署的副本；
3. 一个请求批次能够分配到多条完整 SFC 路径；
4. 目标函数只有预计总成本，不增加人工权重；
5. CPU、内存、故障、可靠性和 SLA 作为硬约束处理；
6. 取整结果的请求总数、容量和路径顺序正确；
7. 求解失败时直接拒绝且不存在回退；
8. 结果包含论文需要的求解状态、目标值和耗时；
9. 核心测试和一个真实慢窗口闭环通过；
10. 新代码包含面向初学者的必要中文注释；
11. 修改提交并推送到 `codex/dppo-main-algorithm` 分支。
